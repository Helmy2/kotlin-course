## The Thread-Per-Request Bottleneck on the Backend

```text
Traditional Blocking Thread-Per-Request (Tomcat 200 Threads):
[HTTP Req] ──► [OS Thread #1 (1MB RAM)] ──► Calls DB (Blocked 150ms) ──► Calls Payment API (Blocked 300ms)
                                             ▲ OS Thread sits completely IDLE for 450ms!

Kotlin Coroutines (Cooperative Suspension):
[HTTP Req] ──► [Coroutine (Few Hundred Bytes)] ──► Calls DB (Suspends!)
                                                    └─► Worker Thread is FREED to serve 1,000 other requests!
```

* **OS Threads are Expensive:** ~1 MB stack allocation per thread; expensive kernel context switches.
* **Coroutines are Ultra-Lightweight:** You can run **100,000+ concurrent coroutines** in a few dozen megabytes of heap memory.
* **Non-Blocking Suspension:** When a coroutine calls a `suspend` function (e.g. `delay()`, `WebClient.awaitBody()`, `R2DBC`), it relinquishes its underlying carrier thread until the response arrives.

## What Does `suspend` Actually Mean Under the Hood?

Marking a function with `suspend` does **not** create a background thread. Instead, the Kotlin compiler transforms the function using **Continuation Passing Style (CPS)**:

```kotlin
// Source Code:
suspend fun fetchUserProfile(userId: String): UserProfile

// Bytecode Generated by Kotlin Compiler:
fun fetchUserProfile(userId: String, continuation: Continuation<UserProfile>): Any?
```

* **The Continuation:** An interface holding the execution stack, local variables, and a completion callback (`resumeWith(Result)`).
* **State Machine:** The function is sliced into states at every suspension point. When an I/O operation completes, the runtime resumes the function at the exact state it paused without tying up an OS thread!

## The Coroutine Builders: `runBlocking`, `launch`, and `async`

| Builder | Return Value | Concurrency | Primary Backend Use Case |
| :--- | :--- | :--- | :--- |
| **`runBlocking`** | `T` (Result of lambda) | **Blocking** | **Bridges non-coroutine worlds:** Top-level `main()` functions or JUnit test methods. *Never call inside production HTTP request threads!* |
| **`launch`** | `Job` | Non-blocking fire-and-forget | Background asynchronous tasks where the caller doesn't wait for a return value (sending emails, audit logs, metrics). |
| **`async`** | `Deferred<T>` | Non-blocking with result | Concurrent tasks where the caller needs the return value (`await()`), e.g., calling 3 downstream microservices in parallel. |

```kotlin
// Parallel decomposition with async:
suspend fun fetchDashboard(userId: String): Dashboard = coroutineScope {
    val ordersDef = async { orderService.getOrders(userId) }
    val loyaltyDef = async { loyaltyService.getPoints(userId) }

    // Await both in parallel:
    Dashboard(orders = ordersDef.await(), points = loyaltyDef.await())
}
```

## The "Async-Style" Anti-Pattern: Returning `Deferred<T>`

> [!WARNING]
> **Anti-Pattern:** Exposing functions that return `Deferred<T>` or launch coroutines on an unbounded global scope (`GlobalScope`).

```kotlin
// ❌ ANTI-PATTERN: Returning Deferred breaks Structured Concurrency!
fun fetchRatesAsync(pair: String): Deferred<Double> = CoroutineScope(Dispatchers.IO).async {
    // Leaks resources if the caller forgets to await() or cancels its parent scope!
    remoteExchangeClient.getRate(pair)
}
```

### Why This is Dangerous in Backend Systems:
1. **Scope Leaks:** The function begins execution immediately in an unmanaged scope. If the caller times out or fails, `fetchRatesAsync` keeps running invisibly in the background.
2. **Hidden Concurrency:** The caller doesn't know if the function is CPU-heavy, I/O-heavy, or which dispatcher it uses.

### The Idiomatic Solution:
```kotlin
// ✅ CLEAN & IDIOMATIC: Regular suspend function
suspend fun fetchRates(pair: String): Double = withContext(Dispatchers.IO) {
    remoteExchangeClient.getRate(pair)
}

// Concurrency is managed explicitly at the call site inside a structured scope:
suspend fun loadSummary() = coroutineScope {
    val rateDeferred = async { fetchRates("USD/EGP") }
    // ...
}
```

## Choosing the Right Dispatcher

The **`CoroutineDispatcher`** determines which thread or thread pool executes the coroutine:

| Dispatcher | Thread Pool Size | What to Run On It |
| :--- | :--- | :--- |
| **`Dispatchers.IO`** | Elastic (Up to 64 threads or core count) | **Blocking I/O:** Traditional JDBC database queries, file system read/write, legacy blocking HTTP calls (`RestTemplate`, `HttpClient`). |
| **`Dispatchers.Default`** | Fixed to CPU core count ($N$ cores) | **CPU-Intensive Tasks:** JSON/XML serialization, complex JWT cryptographic verification, large list sorting/filtering. |
| **`Dispatchers.Unconfined`** | Starts in current thread, resumes in whatever thread completes suspension | Fast event dispatchers. Avoid in standard business backend logic. |

```kotlin
// Switching context safely with withContext:
suspend fun readConfigAndHash(file: File): String {
    // 1. Switch to IO pool for disk reading
    val rawBytes = withContext(Dispatchers.IO) {
        file.readBytes()
    }
    // 2. Switch to Default pool for heavy SHA-256 calculation
    return withContext(Dispatchers.Default) {
        MessageDigest.getInstance("SHA-256").digest(rawBytes).toHex()
    }
}
```

## Structured Concurrency: Parent-Child Relationships

Unlike raw Java threads that run detached until process death, Kotlin coroutines obey **Structured Concurrency**:

```text
               CoroutineScope (Parent Job)
                     /             \
                    /               \
         Child Job #1 (async)    Child Job #2 (async)
```

1. **Child scopes inherit context:** Dispatchers, exception handlers, and correlation IDs are inherited.
2. **Parents wait for children:** A parent scope cannot complete until all its child coroutines finish.
3. **Cancellation cascades downwards:** If a parent is cancelled, all active children are cancelled instantly.
4. **Failures cascade upwards:** If a child fails with an unhandled exception, it cancels its parent and all sibling coroutines!

---

## `coroutineScope` vs. `supervisorScope`

| Scope Builder | Failure Propagation Behavior | When to Use in Backends |
| :--- | :--- | :--- |
| **`coroutineScope`** | **Fail-Fast (All-or-Nothing):** If one child fails, all sibling coroutines are immediately cancelled and the error is rethrown. | Dependent workflows: e.g., placing an order requires *both* inventory lock AND payment auth. If payment fails, cancel inventory lock immediately! |
| **`supervisorScope`** | **Resilient (Isolated Failures):** If one child fails, sibling coroutines **continue running**. The error does not cancel the parent. | Independent microservice aggregation: e.g., Dashboard loads Profile, Loyalty Points, and Recommendations. If Recommendations fails, still show Profile and Points! |

## Cancellation Internals & Resource Safety

Coroutines are **cooperatively cancellable**. Calling `job.cancel()` sets an internal state flag—it does **not** violently preempt CPU instructions!

### The Three Rules of Cancellation:
1. **Long CPU Loops Must Check Cancellation:**
   ```kotlin
   while (hasMoreData) {
       ensureActive() // Or check if (!isActive) break, or call yield()
       processChunk()
   }
   ```
2. **Never Swallow `CancellationException`:**
   ```kotlin
   try {
       callDownstreamService()
   } catch (e: Exception) {
       // ❌ BAD: Swallows CancellationException, breaking parent cancellation!
   } catch (e: CancellationException) {
       throw e // ✅ ALWAYS rethrow CancellationException!
   }
   ```
3. **Guaranteed Cleanup with `NonCancellable`:**
   ```kotlin
   val dbTx = openTransaction()
   try {
       executeTransfer()
   } finally {
       // A cancelled coroutine CANNOT invoke suspend functions unless wrapped in NonCancellable:
       withContext(NonCancellable) {
           dbTx.rollback() // Runs safely even if the HTTP request was aborted!
       }
   }
   ```

## Distributed Tracing & MDC with `ThreadLocal.asContextElement()`

In production logging (Slf4j MDC), trace IDs (`X-Correlation-ID`) are stored in a `ThreadLocal`. Because coroutines suspend and resume on **different threads**, MDC context is lost across suspension points unless explicitly propagated!

Kotlin provides **`ThreadLocal.asContextElement()`** to snapshot and restore `ThreadLocal` state across thread boundaries automatically:

```kotlin
import kotlinx.coroutines.asContextElement
import org.slf4j.MDC

val mdcContext = MDC.getCopyOfContextMap() ?: emptyMap()

// Create a CoroutineContext element that binds MDC to the coroutine:
val traceContext = myThreadLocalTraceId.asContextElement(value = "TX-TRACE-9002")

launch(Dispatchers.IO + traceContext) {
    // Log statement on Thread-1:
    log.info("Processing order...") // Contains [TX-TRACE-9002]

    delay(100) // Suspends! Resumes on Thread-3

    // Thread-3 automatically restores [TX-TRACE-9002]!
    log.info("Order processed successfully")
}
```

## Lab 1: Resilient Multi-Service Checkout Aggregator

**Scenario:** Implement a checkout aggregator that calls 3 downstream microservices concurrently:
1. `fetchSubtotal` (Critical — If this fails, cancel all others and fail).
2. `fetchLoyaltyPoints` (Non-Critical — If this fails, fallback to `0` points).
3. `estimateShipping` (Non-Critical — Timeout after `300ms`, fallback to flat `50.0` fee).

---

## Lab 1: Reference Solution

```kotlin
import kotlinx.coroutines.*

data class CheckoutSummary(
    val orderId: String,
    val subtotal: Double,
    val loyaltyPoints: Int,
    val shippingFee: Double,
    val warnings: List<String>
)

class DownstreamGateways {
    suspend fun fetchSubtotal(id: String): Double { delay(150); require(id.startsWith("ORD-")); return 1200.0 }
    suspend fun fetchLoyalty(userId: String, fail: Boolean): Int { delay(180); if (fail) error("Loyalty offline"); return 350 }
    suspend fun fetchShipping(city: String, slow: Boolean): Double { delay(if (slow) 600 else 100); return 40.0 }
}
```
---
```kotlin
class ResilientAggregator(private val gateways: DownstreamGateways = DownstreamGateways()) {
    suspend fun buildSummary(orderId: String, userId: String, city: String, failLoyalty: Boolean, slowShipping: Boolean): CheckoutSummary = supervisorScope {
        val warnings = mutableListOf<String>()

        val subtotalDef = async { gateways.fetchSubtotal(orderId) }
        val loyaltyDef = async { gateways.fetchLoyalty(userId, failLoyalty) }
        val shippingDef = async { withTimeout(300L) { gateways.fetchShipping(city, slowShipping) } }

        // Critical call: Failure cancels siblings and bubbles up
        val subtotal = try {
            subtotalDef.await()
        } catch (ex: Throwable) {
            loyaltyDef.cancel()
            shippingDef.cancel()
            throw ex
        }

        val loyalty = try { loyaltyDef.await() } catch (e: Exception) {
            warnings.add("Loyalty unavailable: ${e.message}"); 0
        }

        val shipping = try { shippingDef.await() } catch (e: Exception) {
            warnings.add("Shipping timed out/failed; flat 50.0 fee applied"); 50.0
        }

        CheckoutSummary(orderId, subtotal, loyalty, shipping, warnings)
    }
}

```
---
```kotlin

fun main() = runBlocking {
    val aggregator = ResilientAggregator()

    println("--- 1. Healthy Run ---")

    println("\n--- 2. Degraded Run (Loyalty Fails & Shipping Times Out) ---")
    println(aggregator.buildSummary("ORD-2", "USR-9", "Cairo", true, true))
}
```

## Lab 2: Distributed Trace Propagation & Non-Cancellable Teardown

**Scenario:** Implement an order settlement service that propagates an `X-Trace-Id` across thread transitions and guarantees that aborted transactions execute an atomic audit rollback inside `withContext(NonCancellable)`.

---

## Lab 2: Reference Solution

```kotlin
import kotlinx.coroutines.*

val traceContext = ThreadLocal<String>()

class AuditedSettlementService {
    suspend fun executeSettlement(txId: String, failMidway: Boolean) = coroutineScope {
        println("[${traceContext.get()}] Starting settlement for $txId on ${Thread.currentThread().name}")

        try {
            withContext(Dispatchers.Default) {
                println("[${traceContext.get()}] Performing fraud validation on ${Thread.currentThread().name}")
                delay(100)
                if (failMidway) throw IllegalStateException("Payment provider rejected settlement")
            }
            println("[${traceContext.get()}] Settlement complete for $txId")
        } finally {
            withContext(NonCancellable) {
                println("[${traceContext.get()}] [CRITICAL TEARDOWN] Releasing database locks for $txId on ${Thread.currentThread().name}")
                delay(50)
                println("[${traceContext.get()}] Database locks released")
            }
        }
    }
}

```
---
```kotlin

fun main() = runBlocking {
    val service = AuditedSettlementService()
    traceContext.set("TRACE-TX-883")

    val job = launch(Dispatchers.IO + traceContext.asContextElement()) {
        service.executeSettlement("TX-9901", failMidway = true)
    }
    job.join()
}
```

## Topic 05 Recap & Key Takeaways

* **Structured Concurrency by Default:** Always launch coroutines within a `CoroutineScope` or `supervisorScope` to prevent orphaned background tasks and resource leaks.
* **Avoid the "Async-Style" Anti-Pattern:** Never return `Deferred<T>` from business functions; declare them as `suspend fun` and let the caller compose concurrency.
* **Choose the Right Dispatcher:** Confine blocking I/O (JDBC, disk) to `Dispatchers.IO` and CPU-heavy operations to `Dispatchers.Default`.
* **Respect Cancellation:** Check `ensureActive()` in long CPU loops, never catch and swallow `CancellationException`, and wrap critical cleanups in `withContext(NonCancellable)`.
* **Propagate Context:** Use `ThreadLocal.asContextElement()` to carry Slf4j MDC trace identifiers across asynchronous thread hops.
