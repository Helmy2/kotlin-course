## Calling Java from Kotlin: Getters, Setters & Properties

Kotlin automatically maps Java's `getX()` / `setX()` methods into Kotlin property access syntax:

```java
// LegacyCustomer.java
public class LegacyCustomer {
    private String fullName;
    private boolean active;

    public String getFullName() { return fullName; }
    public void setFullName(String fullName) { this.fullName = fullName; }
    public boolean isActive() { return active; }
    public void setActive(boolean active) { this.active = active; }
}
```

```kotlin
// CustomerService.kt
fun inspectCustomer(javaCustomer: LegacyCustomer) {
    // Accessed as properties—no getFullName() / setFullName() needed!
    javaCustomer.fullName = "Tarek Mansour"
    if (javaCustomer.isActive) {
        println("Active customer: ${javaCustomer.fullName}")
    }
}
```

## The Danger Zone: Platform Types (`T!`)

Because Java does not enforce null safety in its type system, any unannotated Java reference arrives in Kotlin as a **Platform Type (`String!`)**:
* **What `T!` Means:** The Kotlin compiler says *"I don't know if this is nullable or non-null—you decide!"*
* **The Trap:** Assigning `String!` to a non-null `val name: String` without checking can cause an immediate `NullPointerException` if Java returns `null`.

```kotlin
// Suppose LegacyRepo.findEmailById(id) is unannotated Java returning String
val rawEmail = legacyRepo.findEmailById("USR-10") // Inferred type: String! (Danger!)

// ✅ Best Practice: Explicitly type every unannotated Java return as Nullable (T?)
val safeEmail: String? = legacyRepo.findEmailById("USR-10")
val normalized = safeEmail?.lowercase() ?: "unknown@domain.com"
```

## Nullability Annotations & JSpecify

When Java code is annotated with nullability contracts, the Kotlin compiler reads them and enforces strict compile-time null safety automatically!
* **Supported Annotation Families:**
    * **JSpecify (`org.jspecify.annotations`):** `@Nullable`, `@NonNull`, `@NullMarked` (Standard in Spring Framework 6.2+ / Spring Boot 3.4+).
    * **JetBrains:** `@Nullable`, `@NotNull`.
    * **Jakarta / Lombok:** `@Nonnull`, `@Nullable`.

```java
// Modern Java with JSpecify:
public class ModernJavaPaymentGateway {
    @Nullable
    public String getAuthorizationCode() { return null; }

    @NonNull
    public String getGatewayVersion() { return "v3.1"; }
}
```
* In Kotlin: `getAuthorizationCode()` is strictly typed as `String?`, and `getGatewayVersion()` is strictly typed as non-null `String`.

## Calling Kotlin from Java: The Polyglot JVM Annotations

When writing Kotlin services, DTOs, or libraries consumed by Java callers, use these four essential `@Jvm*` annotations:

| Annotation | Placement | Problem It Solves in Java |
| :--- | :--- | :--- |
| **`@JvmStatic`** | Function in `companion object` or `object` | Allows Java to call `MyService.execute()` as a true `static` method instead of `MyService.Companion.execute()` or `MyObject.INSTANCE.execute()`. |
| **`@JvmOverloads`** | Function/constructor with default arguments | Generates $N$ overloaded Java methods covering every combination of default parameters. |
| **`@JvmField`** | Property in class or companion | Exposes the field directly as a `public` field without generating getter/setter methods. |
| **`@Throws`** | Function throwing checked exceptions | Emits a Java `throws IOException` clause in bytecode so Java callers can catch checked exceptions. |

---

## Code Example: The 4 Polyglot Annotations in Action

```kotlin
class TransactionExporter @JvmOverloads constructor(
    val exportDirectory: String,
    val includeFees: Boolean = true,
    val maxBatchSize: Int = 1000
) {
    companion object {
        @JvmField
        val DEFAULT_FORMAT: String = "CSV" // Public static final in Java bytecode!

        @JvmStatic
        fun getSupportedFormats(): List<String> = listOf("CSV", "JSON", "PARQUET")
    }

    @Throws(java.io.IOException::class)
    fun writeToDisk(data: String) {
        if (data.isBlank()) throw java.io.IOException("Export data is empty")
        // Write file...
    }
}
```

```java
// Java Caller: Clean, natural Java idiomatic access!
TransactionExporter exporter = new TransactionExporter("/var/exports"); // @JvmOverloads
String format = TransactionExporter.DEFAULT_FORMAT;                    // @JvmField
List<String> formats = TransactionExporter.getSupportedFormats();      // @JvmStatic

try {
    exporter.writeToDisk("sample-data");                               // @Throws
} catch (IOException e) {
    System.err.println("Export failed: " + e.getMessage());
}
```

## Annotation Use-Site Targets (`@field:`, `@get:`, `@param:`)

When a property is declared in a primary constructor, Kotlin creates **multiple bytecode elements**:
1. A **constructor parameter** (`@param:`)
2. A **private backing field** (`@field:`)
3. A **getter method** (`@get:`)
4. A **setter method** (`@set:`) if declared with `var`

If you place a framework annotation without a use-site target, frameworks like Spring Validation, Jackson, or JPA may inspect the wrong bytecode element and silently fail!

```kotlin
import jakarta.validation.constraints.NotBlank
import jakarta.validation.constraints.Size
import com.fasterxml.jackson.annotation.JsonProperty

data class CreateUserRequest(
    // ❌ WRONG: @NotBlank lands on the constructor param; Spring Validator inspects getters/fields!
    // @NotBlank val username: String,

    // ✅ CORRECT: Target the backing field or getter explicitly:
    @field:NotBlank(message = "Username cannot be blank")
    @field:Size(min = 3, max = 50)
    val username: String,

    @field:JsonProperty("customer_email")
    val email: String,

    @get:JvmName("hasVipStatus") // Explicit bytecode method name
    val isVip: Boolean
)
```

## Use-Site Target Decision Matrix for Backend Frameworks

| Target | Bytecode Location | Primary Backend Framework Use Case |
| :--- | :--- | :--- |
| **`@field:`** | Private backing field | Hibernate / JPA mappings (`@Id`, `@Column`), Spring Validation (`@NotNull`, `@Size`), Jackson `@JsonProperty` |
| **`@get:`** | Getter method | Spring Security `@PreAuthorize`, Jackson `@JsonGetter`, Custom bytecode names `@get:JvmName` |
| **`@param:`** | Constructor parameter | Spring Dependency Injection `@Qualifier`, Jackson `@JsonProperty` on deserialization |
| **`@set:`** | Setter method | Spring Property Injection `@Value("\${api.url}")` |

## Functional (SAM) Interfaces (`fun interface`)

A **Single Abstract Method (SAM)** interface can be marked with `fun interface` in Kotlin. This allows callers to pass idiomatic lambdas instead of anonymous classes:

```kotlin
fun interface PaymentValidator {
    fun validate(paymentId: String, amount: Double): Boolean
}

// 1. Pass lambda directly (SAM conversion):
val minimumAmountValidator = PaymentValidator { id, amount ->
    amount >= 10.0
}

// 2. Used in services:
class CheckoutService(private val validator: PaymentValidator) {
    fun process(id: String, amount: Double) {
        if (!validator.validate(id, amount)) {
            throw IllegalArgumentException("Validation failed for payment $id")
        }
        println("Processing payment #$id: $$amount")
    }
}

val service = CheckoutService { id, amount -> amount <= 50_000.0 }
service.process("TX-101", 1200.0)
```

## Framework Plugins: `all-open` & `no-arg`

Kotlin classes are **`final` by default**, and primary constructors do not generate a parameterless constructor unless default arguments are provided for all fields.

### Why Spring & Hibernate Require Gradle Compiler Plugins:
* **Spring CGLIB Proxies:** Spring requires `@Service`, `@Component`, and `@Transactional` classes/methods to be `open` for CGLIB bytecode proxies to intercept transactions and cache lookups.
* **Hibernate Entity Instantiation:** Hibernate / JPA requires a `protected` or `public` no-argument constructor to instantiate entities via reflection.

### Gradle Configuration (`build.gradle.kts`):
```kotlin
plugins {
    kotlin("jvm") version "2.0.0"
    kotlin("plugin.spring") version "2.0.0" // Automatically opens @Component, @Service, @Transactional!
    kotlin("plugin.jpa") version "2.0.0"    // Automatically generates zero-arg constructor for @Entity!
}
```

## Lab 1: Polyglot Java/Kotlin Microservice Gateway

**Scenario:** You are migrating a mission-critical billing microservice from Java to Kotlin. Java services call your Kotlin components, and your Kotlin service must consume legacy Java records while strictly respecting Spring validation and JPA proxying rules.

**Tasks:**

4. Implement a `CreatePaymentCommand` using `@field:` use-site targets for Spring Bean Validation.

## Lab 1: Reference Solution

```kotlin
import java.io.IOException

// 1. Simulating Legacy Java class with platform types
class LegacyJavaAuditRecord(
    val eventId: String,       // In real life, String! from Java
    val actorUsername: String?, // Nullable Java field
    val severityCode: Int
)

// 2. Spring validation DTO with correct use-site targets
data class CreatePaymentCommand(
    @field:jakarta.validation.constraints.NotBlank
    val accountId: String,

    @field:jakarta.validation.constraints.Positive
    val amountPiasters: Long
)

```
---
```kotlin

// 3. Kotlin Service designed for seamless Java consumption
class AuditEntry private constructor(
    val eventId: String,
    val actor: String,
    val severity: String
) {
    companion object {
        const val UNKNOWN_ACTOR = "SYSTEM_AUTOMATION"

        @JvmStatic
        fun fromLegacy(legacy: LegacyJavaAuditRecord): AuditEntry {
            val safeActor = legacy.actorUsername?.trim()?.takeIf { it.isNotBlank() } ?: UNKNOWN_ACTOR
            val mappedSeverity = when (legacy.severityCode) {
                1 -> "LOW"
                2 -> "MEDIUM"
                3 -> "HIGH"
                else -> "CRITICAL"
            }
            return AuditEntry(legacy.eventId, safeActor, mappedSeverity)
        }
    }

    @JvmOverloads
    @Throws(IOException::class)
    fun exportToDisk(filePath: String, compress: Boolean = false): String {
        if (filePath.isBlank()) throw IOException("Invalid file path")
        val mode = if (compress) "GZIP" else "RAW"
        return "Exported [$eventId] by [$actor] to $filePath (Mode: $mode)"
    }
}

```
---
```kotlin

fun main() {
    val legacy = LegacyJavaAuditRecord("EVT-77", null, 3)
    val entry = AuditEntry.fromLegacy(legacy)
    println("Mapped Entry: id=${entry.eventId}, actor=${entry.actor}, sev=${entry.severity}")
    println(entry.exportToDisk("/var/log/audit.log"))
}
```

## Topic 04 Recap & Key Takeaways

* **Defend Against Platform Types (`T!`):** Always explicitly declare unannotated Java returns as nullable (`T?`) to force null-checking before use.
* **Master Use-Site Targets:** Apply `@field:` for JPA and Spring validation annotations on constructor properties so annotations land on bytecode fields rather than constructor parameters.
* **Make Kotlin Friendly to Java:** Use `@JvmStatic`, `@JvmOverloads`, `@JvmField`, and `@Throws` to eliminate clumsy `.Companion` or `.INSTANCE` calls in Java.
* **Use Gradle Compiler Plugins:** Apply `kotlin("plugin.spring")` and `kotlin("plugin.jpa")` to automatically handle `all-open` proxies and `no-arg` Hibernate constructors.
* **Functional SAM Interfaces:** Mark single-method interfaces with `fun interface` for clean lambda interoperability across Kotlin and Java.
